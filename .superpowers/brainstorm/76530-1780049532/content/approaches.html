Implementation approaches

The feature is well-defined — the key question is how we deliver it. Three options.

A

Thin vertical slice first Recommended

Build the full stack for the simple case end-to-end before tackling the complex split logic. Phase order: Schema + migration → Settings page (VAT rate + entities) → entity on items → entity auto-detection on invoice capture → then quantity allocation split modal → reports filtering → import template.

Pros

  • Working app at every step — you can use entities and see them flowing through invoices before the hard modal work starts
  • The plumbing gets battle-tested on the simple case before the complex case is built on top
  • If the split modal takes longer, the rest of the feature is already usable

Cons

  • Slightly different order to the Trello card phases — needs a conscious re-ordering
B

Trello card phases exactly

Follow the card's 5-phase order verbatim: Schema → IPC layer → Invoice capture (including split modal) → Import template → Reports. Complete each phase fully before starting the next.

Pros

  • Matches the existing spec exactly — no re-ordering or re-planning
  • Invoice capture phase is complete in one go, no revisiting

Cons

  • Phase 3 (invoice capture + split modal) is the biggest, most complex phase — nothing is usable until it's done
  • The split modal is hard to get right first time; better to have the simpler flow proven before building on top
C

Settings + Schema only, then pause

Deliver just the schema migration, Settings page (entities + VAT rate), and item entity assignment first — as a standalone shippable. Treat invoice capture changes and reports as a follow-on card.

Pros

  • Smallest possible first merge — foundation is in prod early
  • Natural split point if time is short

Cons

  • The feature isn't actually useful until invoice capture and reports are done — entities exist but do nothing
  • Creates a half-finished state in prod that could confuse the operator

My recommendation: A. Get entities flowing through the whole app on the simple (entity-pure) case first. The split modal is the riskiest part of this feature — you want everything else proven before you build it.
